# ScreenConnect consoles turned against customers as N-central returns

2026-11-12 · [listen](https://raw.githubusercontent.com/lab522/522AM/main/episodes/2026-11-12.mp3)

Brought to you by [Lab522](https://www.lab522.co.uk)

*Attackers are using compromised ScreenConnect consoles to plant remote-access clients on customer machines. N-central has a hotfix and Apache has an unauthenticated code-execution fix, while Xen Orchestra faces a second, still-unpatched flaw.*

Good morning, it's 5:22 AM. Thursday, the twelfth of November, twenty twenty-six.

Someone's using MSPs' own ScreenConnect consoles to install a second remote-access client on customer machines — one the legitimate provider doesn't control. Huntress found the campaign yesterday and is tracking six compromised MSPs, with two hundred and eighty-six endpoints affected across forty-seven organisations. The count's still climbing.

ScreenConnect is ConnectWise's remote-support platform. Attackers are using its Run Command feature to plant rogue clients; Huntress reckons they're abusing legitimate functionality through stolen credentials or hijacked operator sessions, rather than exploiting a software flaw. ConnectWise confirms unauthorised partner-account access and has disabled five third-party extensions across roughly four hundred partner environments as a precaution.

If you run it on-premises, you need to disable those extensions yourself: Labtech Plus and both RMM Plus variants, written as RMM Plus and RMM+. Also disable their Password Link variants, RMM Plus Password Link and RMM+ Password Link. Don't reinstall or re-enable them until further guidance. Cloud-hosted environments have had that done for them, but it removes nothing already planted. Check authentication and administrative activity, including extension installations. Review Run Command history and Toolbox records even without alerts.

And here's the nasty catch: Huntress warns that opening an interactive session to an infected customer machine can compromise the technician's workstation too. ConnectWise is still confirming those reports. I'd investigate with separate security tools, not the remote-support session that could bring the problem home.

Different vendor, different incident, but there is movement on yesterday's missing N-central fix. N-able has released 2026 point 4 Hotfix 2, build 2026 point 4 point 1 point 26. Hosted regions are upgraded and back online; on-premises customers should now follow the upgrade guidance before restoring normal access, then update agents and probes. Built-in remote control is temporarily disabled.

There are seven patched CVEs at last, but no mapping to the thirty-three published issues, whose exploit code remains public. That isn't proof that twenty-six remain open; it is a question N-able still needs to answer. Bales confirms he never disclosed the flaws to the company. WatchTowr has seen exploitation attempts against honeypots, while Shadowserver's exposed-server count has fallen from thirteen hundred and thirty-eight to just over a hundred and forty-eight. Expect another hotfix, and keep hunting on the management server and the systems beneath it.

Away from management consoles, Apache has a patch I'd move ahead of the routine web-server cycle. CVE-2026-119618 is a race in mod_http2's assign_headers function: concurrent threads mishandle shared resources, causing heap corruption that can become code execution with the web-server process's privileges. The attacker reaches it over HTTP/2 without authentication.

If you use HTTP/2 on Apache HTTP Server from 2 point 4 point 55 through versions below 2 point 4 point 71, upgrade to 2 point 4 point 71 or later. Standalone mod_h2 builds from 2 point 0 point 8 through 2 point 0 point 42 need updating past that range. Otherwise remove h2 and h2c from the active protocols line in httpd.conf. Check bundled builds and container images too. Wiz says sixty-four per cent of cloud environments contain vulnerable resources, before configuration is considered; it reports no available exploit or known exploitation.

Back to attacks already happening: Xen Orchestra's attacker is also using an admin-only zero-day involving malicious VM imports to compromise XCP-ng hosts, and that second flaw has no fix yet. The revised upgrade targets are 6 point 9 point 2 or 6 point 10 point 1, but keep management access isolated: Vates says unauthorised access isn't logged and confirmed compromise warrants full reinstallation. Meanwhile, Cynet blocked PowerShell reverse-shell attempts against Qlik Sense analytics servers at several EU customers; the entry flaw is unknown, so update lingering 2023 Enterprise for Windows builds and hunt for PowerShell launched by scheduler.exe. The staging server also held ActiveMQ and Veeam exploits, making those patch checks worthwhile.

For the desktop queue, move Zoom Workplace for Windows to 7 point 1 point 8 or later: it fixes two flaws, including a nine point six unauthenticated privilege escalation reachable over the network. And yesterday's Ivanti batch now has useful targets: CSA 5 point 0 point 8 point 1 fixes missing authentication, while Endpoint Manager 2024 SU8 fixes a nine point eight SQL injection; take the Sentry and EPMM code-execution fixes too. Citrix has six XenServer fixes alongside AMD CPU mitigations.

That component-patching work reaches the factory floor as well: Siemens has nine new advisories covering ten flaws, with two mapping Node2Shell exposure to its products; attempts against Node2Shell have been seen, but none specifically targeting Siemens products. Match those two advisories first and apply mitigations where patches aren't available; Schneider Electric added one medium-severity advisory, and VDE CERT eight more, several involving third-party components.

I'd give the ScreenConnect investigation a separate route in, before anyone opens a support session out of habit. And I'd keep the N-central recovery ticket open until the remaining coverage questions have answers. Hope Thursday gives you a quieter patch window.
