# Cloud breaches leave customers checking identities and rotating secrets

*Microsoft confirms exploited Entra Connect Health exposure, while Rackspace Spot customers face credential rotation after attackers read Kubernetes Secrets. GPGME needs patching, and the medical-imaging flaw discussed yesterday still has no fixed release. Also, an apparent FBI database intrusion and BADBOX's return.*

Good morning, it's 5:22 AM. Sunday, the twenty-second of November, twenty twenty-six.

Microsoft's own cloud is the breached party today. Attackers exploited its Entra Connect Health API to read tenant metadata, including administrator email addresses. That's the service monitoring on-premises identity infrastructure from the cloud, so hybrid identity teams should check Azure Service Health for a notification.

Microsoft found the flaw on the ninth of November, fixed it server-side on the nineteenth and finished investigating on the twentieth. Ten days from discovery to the fix. What bugs me is that customers still don't know when exploitation began, or how many tenants were affected.

The exposed information includes tenant configuration and directory synchronisation status, alongside technical contacts and administrator addresses. Microsoft says passwords and usable credentials weren't exposed; an included registration certificate had expired, and its internal service was already retired. The investigation also identified a possibility of monitoring configuration changes, although Microsoft's notification says it found none.

There's no customer patch to install. There is checking to do: review Connect Health monitoring settings for changes, then examine Entra audit and sign-in logs. Microsoft's script at aka dot ms slash ConnectHealth slash scripts lists exposed metadata types, but shows today's values, not necessarily what attackers saw. I'd warn the service desk and named administrators now. An attacker with your tenant details has a much better opening line than ‘Dear customer’.

With Rackspace Spot, the managed Kubernetes service, the exposure goes beyond a convincing introduction. Intruders used leaked credentials on the seventeenth to act as legitimate users, creating pods and reading customer Kubernetes Secrets. Those secrets can unlock services well beyond the cluster. Rackspace learnt of the intrusion from a customer the next day.

It revoked affected sessions and tokens, removed unauthorised pods and rotated keys. But the administration console outage also stopped customers managing clusters or rotating credentials; service was fully restored yesterday. That's a particularly painful lockout.

If you run affected Spot clusters, rotate every credential held in their Secrets. Reissue Spot API tokens and replace automation refresh tokens, then download fresh Kubernetes configuration files. Use Rackspace's published indicators to hunt, and review the services those credentials unlock for suspicious use back to the seventeenth. Rackspace hasn't answered how many customers were affected or whether customer data was stolen.

From credentials being read to code that reads keys: GPGME, the library applications use to work with GnuPG, has a critical double free. A malicious OpenPGP key with an unusually long user ID triggers it; signed data sent to an application can provide the route, without a manual key import.

The clever, unpleasant bit is the bookkeeping. Parsing moves data into a larger buffer, but an intervening error can leave the old address recorded. Cleanup then frees memory that's already been freed. CVE-2026-129975 affects GPGME before 2 point 3 point 0 and could expose application data; code execution hasn't been ruled out. No exploitation is known.

Update to 2 point 3 point 1, or use the advisory patch or legacy 1 point 24 point 4. On Windows, Gpg4win 5 point 1 point 2 includes the fix. Bundled and statically linked copies need rebuilt applications: updating the system library won't reach them. That's the bit I'd put explicitly in the ticket. GPGMEPP and GPGMEQT don't need updates, and there's no interim workaround.

And yesterday's medical-imaging zero-day now has a name: CVE-2026-133968, upload path traversal in MONAI Label 0 point 8 point 5 and earlier, with authentication off by default. A source fix was merged on the nineteenth of October, but there's still no fixed release: block untrusted network access and enable authentication; check any source build contains that fix.

Away from the patch queue, the FBI is reportedly investigating an apparent intrusion into its National Crime Information Center, the police information database; CNN broke the story and an Associated Press source corroborated it. The FBI hasn't confirmed it, and neither the route in nor any data theft is established, so treat it as developing news rather than an actionable alert. Meanwhile, HUMAN's Satori researchers say BADBOX 3 point 0 is generating forty billion fraudulent ad bids daily through infected Android devices, with a module enrolling devices in one of eleven residential proxy networks without consent. If you have uncertified Android boxes on your network, isolate them from important systems and investigate unexplained traffic even when nobody's watching.

I'd put affected Spot credential rotation ahead of waiting for a fuller breach count. For GPGME, check the applications carrying their own copies, not just the package manager's answer. Hope Sunday gives you a quiet window to get it done.
